## 🔴 CRITICAL

### app/bg-remover/page.tsx:1257 — Ledger mirror clobbers restored batches' LEDGER_KEY meta, un-stamping previously shipped images so they re-export
**[data-loss · Cleanup (bg-remover) & bg pipeline]** The in-memory `ledger` state (517) is seeded only from the in-tab session snapshot, which module-scope session-store loses on any reload/crash. handleLoadedFile re-stamps rows from loaded.meta[LEDGER_KEY] but never calls setLedger. The mirror effect (1257-1271) rewrites LEDGER_KEY wholesale from `ledger` the first time it becomes non-empty — so the first export or seal in a reopened session (runPlan:2491) replaces the durable ledger meta with rows for ONLY the new batch. On the next open, previously shipped images are un-stamped (stored-stamp rows via the drop-stamp rule at 462-468; never-stored-stamp rows — the common case, since bgCodec.signatureOf excludes `batch` — simply never get stamped) and return to the unexported cohorts, so the same pictures ship again in a second ZIP under different numbers, and the batch history is destroyed. The data to prevent this survives in doc.batchIds (restored into batchIdsRef at 437) but the restore path never consults it for stamping; the fix is to seed the LEDGER_KEY mirror (or handleLoadedFile's stamping) from the union of the surviving meta/batchIds rather than from the in-memory ledger alone.

### app/compositor/page.tsx:953 — Editing a band's tile count destroys composed tiles keystroke-by-keystroke
**[data-loss · Compose]** setBandCount windows the band's queue destructively: lowering slices composed tiles off the tail, raising rebuilds the gap as fresh un-composed rows with new ids. The count field (grid-bands.tsx:128) commits per keystroke, so typing a two-digit count transits through a tiny intermediate value and destroys every tile above it; the file-store pump immediately deletes the orphaned records and blobs from IndexedDB. Each destroyed tile is a paid Azure generation. Fix: on lower, park the sliced items instead of dropping them (or reconcile against band.records on raise the way reconcileQueue does), and/or commit the field on blur/Enter.

### app/compositor/page.tsx:528 — Single-mode CSV drop silently deletes all parked banner-grid tiles
**[data-loss · Compose]** reconcileQueue drops parked band rows on the floor: it skips them when building the reuse map but also omits them from its return value, and setItems replaces the entire queue with it. One CSV drop in single mode permanently deletes every banner-grid tile (state, IDB records, and blobs) with no confirmation. The orphaned bandSheets and lean bands survive in the doc, so the file reopens as a grid of empty bands. Fix: return `[...existing.filter(it => it.bandId), ...records.map(...)]` (and similarly preserve image rows if they can ever coexist).

### app/image-generator/page.tsx:464 — After reload of a list-driven Generate file, the first keystroke in the empty Prompts box wipes every restored row and deletes their paid images from disk
**[data-loss · Generate]** handleLoadedFile restores subject rows but never seeds `subjects`, while resolveOpen's localStorage resume pointer guarantees the reload reopens the file. The empty Prompts textarea is live, and its first keystroke reconciles the whole queue against a one-character list, dropping every restored row; the file-store pump then treats the missing ids as deletions and erases their records and Azure image blobs from disk. Fix direction confirmed viable: dropItems (744) already resyncs subjects via formatPromptList — handleLoadedFile should do the same for restored subject rows (setSubjects(formatPromptList(loaded.items.map(it => it.subject ?? '').filter(Boolean))) when the doc has no csvName).


## 🟠 HIGH

### lib/files/use-file-store.ts:269 — Editing a trashed file never clears deletedAt; resumed work is purged without a trash stage
**[data-loss · File store & homepage]** A soft-deleted file in Trash is still a working card: its Link navigates and requestOpen opens it (file-card.tsx:70-79), and editing proceeds normally. The header writer's patch (use-file-store.ts:269-283) preserves base.deletedAt while bumping updatedAt, and nothing else in the open/write path clears deletedAt — only the homepage Restore button (files-home.tsx:120-122) and the Keep toggle (store.ts:168) do. So a file the sweep trashed can carry its old deletedAt stamp through weeks of new paid Azure work. The purge branch (sweep.ts:96-101) requires only updatedAt > 7d idle (cursor bound) plus deletedAt >= PURGE_MS old — both true by then — so the first homepage visit after 7 idle days HARD-deletes the file, silently (no purge toast), skipping the second 7-day Trash window the module's own header promises ("a user who comes back from leave... has a week to notice", sweep.ts:5-9). Partial mitigation, not a fix: the tool's keep-chip shows a "Deletes in N days" countdown derived from deletedAt (which, unlike a live file's, never resets on edit), but nothing says the file is in Trash. Fix: clear deletedAt on any content write (or on open of a trashed file), mirroring handleRestore.

### lib/files/store.ts:310 — A deleted file silently resurrects from the session-store snapshot on the next rail click
**[bug · File store & homepage]** deleteFile clears the pending open request and the localStorage resume pointer but never the module-scope session snapshot — clearSession exists for exactly this and is called by nothing. Same-tab flow: open a Cleanup file, click Home (unmount saves a snapshot carrying fileId, app/bg-remover/page.tsx:738), delete the file and confirm the 'removed for good' dialog (the tab's own lock can't refuse it, store.ts:288), then click Cleanup in the rail. resolveOpen returns the snapshot's fileId (open.ts:144), the page mounts adopted with the old queue on screen, readFile→null is not an error, `known` is empty so the first pump pass re-writes every row's blobs, and the header writer re-mints the header — the deleted file reappears on the homepage with all content and bytes. The same works cross-tab against a tab that navigated away >30s ago. The sweep guards against snapshot-live files via liveFileIds() (files-home.tsx:75); deleteFile has no equivalent, so the confirmed permanent delete is silently undone and the quota it freed is re-consumed. Fix: on delete (local and on the 'deleted' broadcast), clear any session snapshot holding that fileId.

### lib/files/codecs/compositor.ts:149 — Compose signature omits urls/row: image-column remaps never persist, reload composes from the wrong images
**[bug · File store & homepage]** composeCodec.signatureOf covers [resultImage, title, offer, status], but updateMapping/remapItem recompute `urls` from a new image-column choice while every signature element can stay identical — so the corrected mapping never reaches the item records, even though the doc faithfully persists the new imageCols. After a reload, restored rows carry the OLD column's urls (itemFromRecord reads d.urls; nothing re-derives from imageCols), and Generate/regenerate fetch and compose from them — silently producing tiles from the wrong images while the mapping panel shows the corrected columns. Precision on the window: any row re-composed AFTER the remap gets its record rewritten (resultImage identity moves) with fresh urls, so the victims are rows remapped but not re-run before the reload — exactly the "fix the mapping, come back later, hit Generate" flow. reconcileQueue on a CSV re-drop has the same hole for `row` (page.tsx:807): reused rows' new sheet positions never persist, so restored row numbering (and export naming derived from it) goes stale after a re-drop that inserted rows. Fix: add urls (and row) to the signature — they are strings/numbers, and rewriting the few affected rows' records is exactly the store's contract.

### app/bg-remover/page.tsx:1611 — manualFlag survives redo/AI-fix: a manually 'cleared' image whose replacement matte is bad ships silently in a clean batch

### lib/bg/engine.ts:427 — Server-model (RMBG-2.0) path flattens the returned cutout onto opaque white, destroying its alpha
**[bug · Cleanup (bg-remover) & bg pipeline]** toCanvas() now unconditionally fills white before drawing any Blob (engine.ts:364-373, added in commit 6385f24 to fix transparent INPUTS arriving at the model on a black field), but the server branch of removeBackground() reuses toCanvas for the sidecar's OUTPUT: `const outCanvas = await toCanvas(outBlob)` (line 427). **[bug · File store & homepage]** The seed comment claims the first pass "does not rewrite a header that already says exactly this — which is also what keeps updatedAt honest on a plain open" (use-file-store.ts:489-490), but the seeded thumbSource:null can never identity-match the Blob thumbSourceOf returns for any file with a result. ### lib/files/store.ts:50 — Background-tab timer throttling defeats the 30s heartbeat staleness threshold
**[race · File store & homepage]** The open-file heartbeat is a 10s setInterval against a 30s staleness threshold, which the module calls "generous on purpose" — but Chromium throttles chained timers in hidden tabs to once per minute after ~5 minutes hidden, so a mounted-but-backgrounded tool page beats every ~60s and its lock reads stale ~30s of each minute. The protections keyed on isHeldElsewhere then fail for exactly the tabs most likely to hold forgotten work: the homepage in another window can delete a file that is open in a hidden tab (~50% of attempts, no "open in another tab" refusal), and the sweep can trash an idle held file. The hidden tab then receives 'deleted', parks its pump (deadRef), and the user returning continues editing with no persistence and no signal (see the separate parked-state finding). Fix options: raise LOCK_STALE_MS well past 60s (the module's own reasoning says the trash-side cost of a longer threshold is one extra sweep cycle), or re-beat on visibilitychange.

### lib/files/use-file-store.ts:378 — No guard against two tabs opening the same file; concurrent pumps interleave and headers last-writer-win
**[race · File store & homepage]** The heartbeat exists only to refuse deletes and sweeps; the open path has no "already held" check at all, so two tabs routinely edit one fileId — via the same homepage card in two tabs, or simply by duplicating a tool tab (the duplicate resolves through localStorage lastOpened to the same file). The design (db.ts:10-11) plans for two tabs on two files; two tabs on one file has nothing. Fix: at open, read the lock and either refuse/read-only the second tab or hand off ownership.
